Command 历史：可逆操作、随机状态回卷与确定性 Replay

游戏运行时需要把玩家操作变成可撤销、可重做、可保存和可重演的动作历史，同时保持随机结果与业务状态一致。

commandreplay

系列目录

很多游戏在实现撤销时，会先想到保存一份状态快照。

玩家每行动一次，就复制当前数据；需要回退时，再把上一份快照覆盖回来。

这种方式简单直接，但很快会遇到问题：

  • 快照应该包含哪些对象；
  • 引用关系如何深拷贝；
  • 随机数状态如何恢复；
  • 撤销后执行新操作时，旧的重做分支怎么办；
  • 存档是否需要保存整个世界；
  • Bug 回放如何知道玩家做过什么；
  • 版本升级后旧快照能否继续读取。

另一种方案是只记录输入。

但原始按键并不总能稳定重建业务动作：

  • 输入映射可能变化；
  • 同一按键在不同状态下含义不同；
  • UI、网络和 AI 可能不经过玩家输入；
  • 帧率和时间源会影响操作解释。

Sakura Framework 的 Command 模块选择记录业务命令历史，并用快照、随机状态和工厂重建补足可逆性。

先说结论：保存动作语义，而不是只保存按键或最终状态

业务命令历史（后文简称“做过什么的账本”）：按确定顺序记录已经执行的可逆业务动作、参数和随机状态边界，并维护当前历史指针。

做过什么的账本位于输入和最终状态之间：

flowchart LR
    A["玩家 / AI / 网络意图"] --> B["业务 Command"]
    B --> C["Execute"]
    C --> D["游戏状态"]
    B --> E["Command History"]
    E --> F["Undo / Redo"]
    E --> G["Replay Export"]
    G --> H["Save / 调试 / 重演"]

它适合：

  • 回合制战斗；
  • 棋盘与卡牌；
  • 解谜；
  • 建造编辑；
  • 战术规划；
  • 局内回退；
  • 确定性测试；
  • 轻量级操作录像。

对于高度连续的物理模拟，它通常需要与状态快照或专门 Rollback 系统结合。

CommandId 是持久化合同

一个可序列化命令至少需要：

  • 稳定 CommandId；
  • Execute()；
  • Undo()；
  • Payload 序列化；
  • Payload 反序列化。

CommandId 不应直接使用运行时类型全名。

类型名会随着命名空间调整、程序集拆分、代码重构和引擎迁移发生变化。

稳定命令标识（后文简称“动作身份证”）：由项目长期维护、独立于具体类名的 Command Key，用于 Replay 和存档中的工厂映射。

例如：

battle.attack
inventory.move-item
map.place-building
dialogue.choose-option

动作身份证一旦进入持久化数据，就应受到版本和迁移策略保护。

它不是为了让反射更方便，而是为了避免 Replay 获得任意类型创建能力。

工厂注册控制可重建动作集合

加载 Replay 时，系统需要根据 CommandId 创建命令实例。

如果直接反射实例化任意类型，外部数据便可能要求运行未授权代码。

因此 Command Service 使用显式工厂目录：

CommandId
→ 已登记 Factory
→ 创建命令
→ 反序列化 Payload
→ 加入待重演历史

命令工厂白名单（后文简称“只重建项目认识的动作”）：只有项目当前 Scope 明确登记的 CommandId 才能从 Replay 恢复。

缺少工厂时，应整体拒绝本次加载并清空半成品历史。

不能跳过未知命令后继续播放，因为后续状态可能建立在被跳过的动作之上。

历史指针统一 Undo、Redo 和分支

Command 历史不是两个互相独立的栈。

更容易解释的模型是：

[C0, C1, C2, C3]
         ↑
     当前指针
  • 指针左侧和当前位置是已执行分支；
  • 指针右侧是可 Redo 分支；
  • Undo 让指针左移；
  • Redo 让指针右移并重新执行；
  • 在中间位置执行新命令时，右侧旧分支被擦除。
flowchart LR
    A["执行 C0、C1、C2"] --> B["Undo C2"]
    B --> C["Undo C1"]
    C --> D["执行新命令 N"]
    D --> E["删除旧 C1、C2 的 Redo 分支"]

系统不应保留一条已经被新行动否定的隐形未来，除非产品明确设计了多时间线。

Snapshot 负责恢复对象，Command 负责表达动作

单纯依靠反向逻辑实现 Undo()，很容易遗漏状态。

例如一次攻击可能同时修改：

  • 生命；
  • 护盾；
  • Buff；
  • 连击；
  • 行动点；
  • 任务计数。

要求每个命令手写完整反向操作，维护成本很高。

状态自愈快照（后文简称“行动前留底”）：命令执行前捕获目标状态，撤销时恢复前置快照。

Command 与 Memento 的分工是：
结构 负责内容
Command 描述执行了什么、参数是什么、如何进入历史
Snapshot 保存目标在执行前的可恢复状态
CommandService 管理顺序、指针、分支和 Replay
Adapter 提供引擎时间、版本和随机状态

行动前留底不意味着复制整个游戏世界。

更合适的是按可逆边界捕获：

  • 单个棋盘；
  • 一组战斗状态；
  • 当前建造事务；
  • 一个编辑文档；
  • 某个业务聚合根。

快照过大会增加内存和序列化成本，过小则无法保证撤销完整。

随机数也属于前置状态

假设一个命令执行时进行了三次随机抽取。

撤销命令只恢复生命和手牌，却没有恢复随机流。下一次重新执行时，结果会不同。

这会破坏：

  • Redo；
  • Replay；
  • Bug 复现；
  • 确定性测试；
  • 回合回退。

因此，Command Service 在执行前记录当前随机抽取次数，并允许 Adapter 注入：

  • Seed Provider；
  • Draw Count Provider；
  • Restore Handler。

随机流回卷（后文简称“连随机进度一起退”）：Undo 时恢复到该命令执行前的随机种子与抽取位置。

只记录 Seed 通常不够。

如果随机生成器已经消费若干次，同一 Seed 的起点无法表示当前进度。

记录 Draw Count 后，Adapter 可以重建随机流：

初始化 Seed
→ 按记录次数推进
→ 回到命令执行前的位置

这要求项目使用可控的伪随机实例，而不是在业务中散落调用不可追踪的全局随机 API。

Replay 导出当前有效分支

玩家执行：

A → B → C

随后 Undo 到 A，再执行 D，真实历史已经变成：

A → D

Replay 不应继续导出被放弃的 B、C。

因此，导出数据只包含当前指针之前的有效分支。

一份轻量 Replay 通常包括：

  • Game Version；
  • 初始状态元数据；
  • Random Seed；
  • Command Sequence；
  • 每条命令的 CommandId；
  • Payload；
  • 可选时间戳；
  • 命令执行前的 RNG Draw Count。

这里的初始状态元数据不一定是完整存档。

它可以是：

  • 关卡 ID；
  • 配置版本；
  • 初始 Deck；
  • 初始棋盘；
  • 战斗种子；
  • 规则集 Revision。

只要项目能够从它重建确定的起点。

Replay 加载与重演分成两个阶段

加载 Replay 时，不应立即修改世界。

更安全的流程是：

  1. 清空当前历史；
  2. 验证 Replay 基础结构；
  3. 恢复随机种子起点；
  4. 逐条查找命令工厂；
  5. 创建命令并反序列化 Payload；
  6. 把命令装入历史；
  7. 将当前指针置于起点；
  8. 由调用方逐步 Redo。
flowchart LR
    A["Replay JSON"] --> B["验证与重建命令"]
    B --> C["历史指针 = -1"]
    C --> D["Redo 1"]
    D --> E["Redo 2"]
    E --> F["Redo N"]

装载与执行分离（后文简称“先把剧本装好，再开始演”）：Replay 解析只重建动作历史，实际状态变化由显式 Redo 推进。

这带来几个好处：

  • 可以逐步播放；
  • 可以在每一步比较状态；
  • 可以暂停和诊断；
  • 可以把重演接入 UI；
  • 可以在执行前完成版本和权限校验。

Command Replay 可以成为 Save Payload

传统存档通常直接保存大量最终状态。

对于动作数量有限、起点稳定的玩法，也可以保存：

初始状态
+ 已提交命令序列

加载时从起点确定性重演。

这种方式的优势包括：

  • 存档结构更接近玩家行为；
  • 容易生成操作历史；
  • 可以用于回放和 Bug 报告；
  • 状态差异可以定位到具体命令；
  • 同一格式能够支持临时检查点。

但它不适用于所有存档。

当一局包含数十万连续操作、实时物理或大量外部状态时，完整重演成本会过高。

更实际的方案可能是：

周期性状态快照
+ 快照后的命令增量

Command 历史需要明确 Scope

Command Service 可以作为 App 级服务登记，但具体历史不应无限跨玩法累积。

项目需要决定：

  • 一个战斗一份历史；
  • 一个关卡一份历史；
  • 一个编辑文档一份历史；
  • 一个玩家会话一份历史。

Scope 结束时应：

  • Clear() 历史；
  • 清空或替换命令工厂；
  • 解绑随机状态访问器；
  • 注销历史事件监听；
  • 释放命令持有的业务引用。

如果 App 级单例永久保存上一局工厂，下一局 Replay 可能重建到已经销毁的目标对象。

服务可以常驻，历史和工厂必须按 Owner 更新。

它不是完整网络 Rollback

Command Replay 容易与帧同步或网络回滚混淆。

当前范式主要解决的是业务动作历史，不自动提供：

  • 每帧输入预测；
  • 状态校正；
  • 客户端回滚重模拟；
  • 物理确定性；
  • 网络快照压缩；
  • 延迟补偿；
  • 跨平台浮点一致性。

网络系统可以复用稳定 CommandId、Payload 和确定性随机思想，但仍需要自己的 Tick、Authority 和 Snapshot 协议。

测试应围绕动作边界

Command 系统的测试不应只验证 Undo 后数值相等。

还应覆盖：

  • 执行失败时不写入历史；
  • Undo 失败时指针不移动；
  • 中间分支执行新命令后 Redo 被清除；
  • 历史超过上限时移除最旧记录；
  • Replay 只导出有效分支；
  • 未登记工厂时加载整体失败；
  • Payload 反序列化异常时不留下半套历史；
  • RNG Draw Count 可以恢复；
  • Clear() 后历史指针回到起点；
  • Scope 销毁后没有事件和目标引用残留。

这些测试共同保护的是“做过什么的账本”可信，而不只是某个命令类能够运行。

我的判断

可撤销和可重演不是两个独立功能。

它们共享同一个基础问题：

游戏是否把重要业务变化表达成稳定、可识别、可恢复的动作。

当 CommandId、Payload、前置快照、历史指针和随机流位置都成为正式合同后，同一套动作历史可以服务于：

  • Undo / Redo；
  • 局内回退；
  • Save Checkpoint；
  • 教学回放；
  • Bug 复现；
  • 自动化验证；
  • 观战与审计的上层适配。

设计检查表

  • CommandId 是否独立于类名和程序集；
  • Replay 是否只允许白名单工厂重建；
  • Payload 是否只包含稳定业务参数；
  • Undo 使用反向逻辑还是前置快照；
  • 快照边界是否足够完整且不过大； -随机 Seed 与 Draw Count 是否可以恢复；
  • 在历史中间执行新命令时是否擦除 Redo 分支；
  • Replay 是否只导出当前有效分支；
  • 加载与实际重演是否分离；
  • 未知命令或反序列化失败时是否整体拒绝；
  • 历史、工厂和随机适配是否属于明确 Scope；
  • 是否错误地把业务 Replay 当成完整网络 Rollback。
