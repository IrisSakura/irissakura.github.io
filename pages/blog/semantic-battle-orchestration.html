语义战斗编排：事件、状态、资格事实与受限动作管线

跨技能、命中、状态和内容扩展的战斗协作，需要在表达能力、确定性、执行权限和调试可追踪性之间建立稳定边界。

essay

系列目录

战斗系统规模较小时，事件直连通常足够有效。

命中
→ 扣血
→ 播放特效
→ 检查被动
→ 触发技能

随着内容增加，同一个命中还可能需要处理：

  • 元素反应；
  • 武器词条；
  • 状态叠加；
  • 连击次数；
  • 受击反应；
  • AI 记忆；
  • 任务统计；
  • Mod 规则；
  • 服务器权威校验。

如果每个模块都直接订阅命中事件，并自行判断其他模块状态，系统会逐渐形成隐式调用网。

一个新效果可能需要知道：

  • 当前目标是否燃烧；
  • 攻击是否来自金属武器；
  • 这是本回合第三次命中还是全局第三次；
  • 该状态由哪个来源授予；
  • 某个扩展是否有权执行对应技能。

问题不再是怎样发出一个事件，而是如何把战斗事实转换成可控、可解释的动作。

先说结论：先描述事实，再生成动作请求

语义战斗编排（后文简称“战斗事实管线”）：把一次性事件、持续状态和资格事实输入确定性规则处理器，生成受限动作请求与结构化 Trace，再由明确 Adapter 执行实际效果。

战斗事实管线不直接替代：

  • Hitbox；
  • GAS；
  • ECS；
  • Simulation；
  • 服务器权威；
  • 具体技能和数值内容。

它位于这些模块之间，负责回答：

已经发生了什么，当前具备什么状态，哪些规则因此成立，以及允许提出哪些动作。

flowchart LR
    A["Hitbox / Simulation 事实"] --> B["Signal Mapper"]
    B --> C["Semantic Combat Processor"]
    D["持续 State"] --> C
    E["Semantic 资格事实"] --> C
    C --> F["受限 Action Request"]
    C --> G["结构化 Trace"]
    F --> H["GAS / Project Adapter"]
    H --> I["实际状态变更"]

三类 Tag 承担不同语义

统一使用 Tag，不等于所有 Tag 都是同一种东西。

战斗编排至少需要区分三类语义。

Event：一次性发生的事实

例如：

  • Event.Hit.Semantic；
  • Event.Damage.Fire；
  • Event.Skill.Cast.Completed；
  • Event.Unit.Died。

Event 表示某件事发生了一次，通常只在本次处理或单 Tick 内有效。

State：持续存在的状态

例如：

  • State.Burning；
  • State.Staggered；
  • State.Shielded；
  • State.Combo.Active。

State 表示对象当前仍处于某种状态，需要明确授予来源、撤销来源和作用域。

Semantic：资格或解释事实

例如：

  • Semantic.Material.Metal；
  • Semantic.Element.Water；
  • Semantic.Target.Boss；
  • Semantic.Attack.Melee。

Semantic 表示规则解释所需的稳定事实。

它未必直接对应一个 Buff，也不一定由 GAS 持有。它可以来自装备、材质、环境、目标分类或项目自己的语义目录。

三类信息放在同一规则语言中，可以表达：

发生金属武器命中
+ 目标当前处于潮湿状态
+ 攻击具备近战资格
→ 提出施加感电与硬直的动作请求

但它们的生命周期和 Owner 仍然不同，不能因为都使用 Tag 就混为一类。

Signal 应保持不可变且受限

如果事件载荷允许携带任意对象引用，规则层会重新耦合到具体项目类型。

例如 Signal 直接带入：

  • GameObject；
  • AbilitySystemComponent；
  • 具体敌人类；
  • Prefab；
  • 任意脚本回调。

规则处理器便无法保持引擎无关，也难以序列化、测试和跨进程验证。

受限结构化载荷（后文简称“只带规则需要的事实”）：Signal 只包含规则判断所需的稳定值、标识和有限字段，不携带可任意执行或修改世界的对象。

常见字段包括：

  • source / target 稳定 ID；
  • sequence；
  • generation；
  • damage category；
  • ability key；
  • rule context revision；
  • 少量数值参数。

规则层看到的是事实快照，而不是对战斗世界的直接控制权。

Rule 输出动作模板，而不是任意代码

一条语义规则通常包含：

  • RuleId；
  • 触发 Event；
  • 必需 State；
  • 禁止 State；
  • 必需 Semantic；
  • 优先级；
  • 动作模板；
  • 幂等与预算策略。

关键边界在于：规则不应保存任意反射类型、程序集入口或脚本函数。

白名单动作模板（后文简称“只能申请已登记动作”）：规则输出固定动作类型和项目登记的 Handler Key，由执行层解析到明确实现。

动作类型可以包括：

  • AddStateTag；
  • RemoveStateTag；
  • RequestAbility；
  • EmitSignal；
  • ApplyModifier；
  • RecordSemanticFact。

Handler Key 只允许映射到项目注册目录。

这使配置表、Mod 或脚本规则只能提出被允许的动作，而不能通过字符串获得任意代码执行权限。

处理器负责确定性，不负责业务效果

语义处理器的职责应保持克制：

  1. 接收 Signal 与当前事实；
  2. 按稳定规则排序；
  3. 检查条件；
  4. 应用幂等作用域；
  5. 消耗处理预算；
  6. 生成动作请求；
  7. 写入 Trace。

它不应：

  • 直接读取 Unity Time；
  • 持有具体 ASC；
  • 加载资源；
  • 查找场景对象；
  • 播放音效；
  • 修改敌人生命；
  • 创建 Prefab。

这样，规则判断可以在纯 C# 环境中重复执行。

同一输入、同一状态和同一规则集合，应产生相同动作序列和原因码。

稳定排序防止内容顺序变成隐藏规则

多个规则同时命中时，执行顺序会影响结果。

例如：

  • 先移除护盾再结算伤害；
  • 先施加湿润再检查感电；
  • 先触发死亡再触发受击；
  • 先消费连击层数再计算奖励。

如果顺序依赖配置文件读取顺序、Dictionary 枚举或程序集扫描，同一内容可能在不同环境中产生不同结果。

因此，规则需要显式优先级，必要时再以 RuleId 作为稳定排序键。

稳定规则顺序（后文简称“相同输入按同一顺序判”）：规则集合不依赖运行时容器和文件自然顺序，任何环境都能得到一致处理次序。

稳定排序不能自动解决所有规则冲突，但至少能让冲突可复现、可测试、可记录。

幂等作用域防止同一事实重复消费

网络重发、事件桥接和多层 Adapter 都可能让同一 Signal 被处理多次。

如果每次都重复：

  • 增加状态；
  • 触发技能；
  • 发放奖励；
  • 记录死亡；

系统会产生难以定位的重复副作用。

语义处理器需要根据 generation、sequence、rule、source 和 battle scope 建立幂等键。

幂等消费（后文简称“同一事实只算一次”）：同一个业务事实在规定作用域内重复进入时，不再生成第二组动作。

幂等不是永久去重。

新一局战斗、下一代实体或新的合法 sequence 应重新允许规则执行，因此战斗结束时需要显式重置处理器或关闭对应 Scope。

单 Tick 预算是内容安全边界

规则可以继续发出事件，事件又可能触发更多规则。

命中
→ 施加燃烧
→ 燃烧触发元素反应
→ 反应发出范围命中
→ 范围命中再次触发被动

如果没有预算，一个配置错误便可能形成无限链。

语义处理预算（后文简称“这一 Tick 最多处理多少”）：限制单次调用中的规则检查数、动作数和派生深度。

预算耗尽时，系统应：

  • 停止继续派生；
  • 返回明确状态；
  • 在 Trace 中记录预算原因；
  • 不隐式扩大上限；
  • 不执行未被完整验证的尾部动作。

预算不是单纯的性能优化参数，而是防止内容错误和扩展规则拖垮主线程的安全合同。

State Store 应记录授予来源

持续状态不能只保存一个布尔值。

假设 State.Burning 同时来自：

  • 地面火焰；
  • 武器词条；
  • Boss 光环。

其中一个来源结束时，不能直接把 Burning 全局移除。

来源聚合状态（后文简称“谁加的就由谁撤”）：State Tag 按 grant source 记录，只有最后一个有效来源被撤销后，状态才真正消失。

同一结构也适用于：

  • 无敌；
  • 沉默；
  • 输入锁定；
  • UI 遮罩；
  • 移动减速；
  • 临时阵营关系。

来源身份使状态生命周期能够与 Battle、Ability、Zone 或 Mod Session 绑定。

Action Request 与实际执行分层

规则处理器输出动作请求后，仍需要 Adapter 做最终执行。

以 GAS 为例，Adapter 可以负责：

  • 解析 Handler Key；
  • 查找项目 Ability Catalog；
  • 验证目标与权限；
  • 调用公开 GAS API；
  • 返回成功或拒绝原因；
  • 把执行结果写入 Trace。

“规则成立”和“动作执行成功”是两个不同事实。

Trace 应分别记录，避免把执行层拒绝误认为规则未匹配。

Trace 是战斗编排的解释接口

复杂战斗 Bug 常见的描述是：

这个被动有时没有触发。

如果系统只保存最终状态，排查时需要猜测：

  • Signal 是否进入；
  • Tag 是否缺失；
  • Rule 是否被禁止状态挡住；
  • 是否命中幂等；
  • 是否预算耗尽；
  • Action 是否生成；
  • Handler 是否存在；
  • GAS 是否拒绝。

结构化 Trace（后文简称“每一步都留下原因”）：为规则检查、动作生成和执行边界记录稳定原因码与关键身份。

一条 Trace 至少应允许回答：

Signal accepted
→ Rule matched
→ Required semantic satisfied
→ Action requested
→ Handler resolved
→ Execution rejected: target-invalid

Trace 可以同时服务于 Runtime Monitor、自动测试、战斗回放、服务器审计和 Mod 调试。

边界比功能数量更重要

语义战斗编排很容易继续扩张成统一战斗框架。

但它应明确不负责：

  • 完整帧同步；
  • 物理碰撞；
  • ECS 调度；
  • 具体数值公式；
  • 资产加载；
  • UI 和音效；
  • 网络复制；
  • 项目内容目录。

这些能力通过 Bridge 接入，而不是进入 Core。

即使 Sample 同时展示 Command、Save、UI、Audio 和脚本规则，也不应扩大 Semantic Combat 父包的硬依赖或稳定 API。

我的判断

战斗系统的可扩展性，不取决于事件总线能连接多少模块。

更关键的是建立一条受约束的转换链：

事实
→ 条件
→ 受限请求
→ 权威执行
→ 可解释结果

当事件、状态和语义资格被分开表达，规则判断与动作执行被分层，预算、幂等和 Trace 成为正式合同后，战斗内容才能在增加组合能力的同时保持可控。

设计检查表

  • Event、State 和 Semantic 是否被明确区分；
  • Signal 是否携带不必要的引擎对象或回调；
  • Rule 是否输出白名单动作，而不是任意类型名；
  • 规则集合是否有稳定排序；
  • 同一事实是否存在幂等键；
  • State 是否按 grant source 聚合；
  • 单 Tick 是否有规则、动作和深度预算；
  • 预算耗尽是否产生明确 Trace；
  • 规则匹配与动作执行结果是否分别记录；
  • GAS、Hitbox、Simulation 和 Server 是否通过 Bridge 接入；
  • Battle 结束时是否重置处理器和状态来源；
  • Sample 扩展是否被误写进父包硬依赖。
