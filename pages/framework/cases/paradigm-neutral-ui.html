CASE 03 · local-passed / runner-pending

Paradigm-Neutral UI

Direct、Binding、MVVM 与 Structured UI 的渐进成本模型

阅读本页返回 Engineering Hub

local-passed / runner-pendingDirect、Binding、MVVM 与 Structured UI 的渐进成本模型

01

Problem

统一 UI 范式会让简单页面过度工程，也会让复杂页面缺少状态边界。

02

Constraints

View 生命周期由 Unity 承担，状态与绑定应可测试；不同 Consumer 的复杂度与团队规模不同。

03

Naive Approach

把 MVVM 设为默认，或让每个 View 直接查找场景和服务。

04

Architecture Decision

共享 UI Core 与状态契约，Direct、Binding、MVVM、Structured 作为递增选择，Unity Presentation 保留平台职责。

05

System Model

State / Intent 位于可测试层；Binding 可选；View 只持有显式依赖并在隐藏或销毁时释放。

06

Failure Model

View 关闭后回调、双向绑定循环、隐藏依赖、异步结果写入失效页面与范式间行为不一致。

07

Trade-offs

多路径扩大测试矩阵，但避免把所有页面强制进同一成本模型。

08

Implementation

UI Production Architecture V2 覆盖 Direct、Binding、MVVM 与 Structured 多种消费路径。

09

Evidence

本地 EditMode 与多 Consumer 回归已闭合；远端 Runner 仍 pending。

10

Consumer

不同示例与玩法项目按页面复杂度选择路径，Framework 不拥有具体视觉、文案和业务流程。

11

Known Limitations

没有真实运行截图作为公开素材；本页使用结构与验证边界，不用品牌图冒充运行证据。

12

What Changed After Validation

验证后把“MVVM 最佳实践”改成 Progressive Architecture Cost，并强化关闭、取消和跨范式一致性测试。
