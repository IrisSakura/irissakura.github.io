交互式文本冒险（Interactive Fiction）

围绕叙事状态、选择条件、分支汇合与文本反馈组织可追踪的互动故事。

interactive-fictionnarrativestate

COMPLETE RESEARCH

完整研究结构

Agent 标签：interactive-fiction narrative state

核心问题：如何让玩家用自然命令探索一个规则一致、会记住行动且能对失败作出有意义回应的文本世界？

一、类型定位与核心抽象

交互式文本冒险的核心不是视觉小说，也不是普通文字剧情。

视觉小说通常以剧情节点、选项和角色路线为核心；交互式文本冒险则以“玩家输入命令，系统解析意图，世界模型根据规则反馈结果”为核心。

它最适合抽象为：

命令解析、世界状态与对象可操作性框架。

核心循环是：

玩家阅读场景描述 → 输入动作命令 → 解析器识别动词、对象和修饰语 → 世界模型检查命令是否合法 → 执行动作规则 → 更新状态谓词 → 输出文本反馈 → 玩家根据反馈继续推理。

玩家真正操作的不是按钮，而是一个由文字描述、对象关系、状态谓词和可交互规则组成的世界。

二、运行时架构

整体架构可以分为九个核心域。

第一是命令输入域。负责接收玩家文本、快捷命令、历史命令、自动补全和别名输入。

第二是语言解析域。负责将“打开木门”“用银钥匙开箱子”“查看桌子下面”等输入转化为结构化动作。

第三是世界对象域。负责维护房间、物品、容器、人物、机关、门、隐藏物、可穿戴物、可阅读物等对象。

第四是状态谓词域。负责维护对象状态，例如门是否打开、箱子是否上锁、钥匙是否在背包中、蜡烛是否点燃、角色是否知道密码。

第五是动作规则域。负责判断动作能否执行，以及执行后如何改变世界。

第六是文本反馈域。负责根据动作结果生成描述、错误提示、暗示、环境变化和叙事反馈。

第七是解谜依赖域。负责维护谜题条件、可达路径、替代解法、软锁保护和线索分布。

第八是记忆与发现域。负责记录玩家已见过的房间、已检查对象、已知信息、已尝试无效命令。

第九是调试与验证域。负责检查命令覆盖、对象不可达、谜题无解、文本反馈缺失和状态冲突。

三、核心数据模型

WorldRoom 表示空间节点，记录房间ID、名称、描述、出口、可见对象、隐藏对象、环境状态和进入条件。

WorldObject 表示世界对象，记录对象ID、名称、别名、类型、所在位置、可见性、可携带性、可操作动作、当前状态和描述文本。

CommandIntent 表示解析后的玩家意图，记录动词、目标对象、工具对象、方向、修饰语、原始输入和解析置信度。

ActionRule 表示动作规则，记录动作类型、目标类型、前置状态、执行效果、失败反馈、成功反馈和后续事件。

StatePredicate 表示世界状态谓词，例如 hasKey、doorOpen、boxLocked、candleLit、npcTrustPlayer。

PuzzleGraph 表示谜题依赖，记录线索、对象、动作、状态变化和解锁路径。

ResponseTemplate 表示反馈文本，记录成功文本、失败文本、部分成功文本、重复尝试文本和提示文本。

四、核心范式一：玩家输入不是选项，而是意图表达

交互式文本冒险最大的特征是玩家可以用自然语言或类自然语言表达意图。

玩家不是从三个按钮中选择“打开门”，而是可以输入：

打开门。 推门。 用钥匙开门。 检查门锁。 踢门。 听门后。

系统需要将不同表达归一为结构化动作。

这要求框架支持动词别名、对象别名、上下文省略和歧义处理。

例如玩家输入“打开它”，系统需要知道“它”可能指上一轮提到的箱子。如果当前房间有两个箱子，系统应提示玩家明确目标，而不是直接失败。

五、核心范式二：世界由对象与状态谓词组成

文本冒险的世界不能只是一段段文字。

它应当是由对象和状态组成的模型。

门是对象。 门有打开、关闭、上锁、损坏等状态。 钥匙是对象。 钥匙可以在桌上、背包里、箱子里。 箱子是容器。 箱子可以上锁，可以被打开，可以包含其他对象。

玩家命令本质上是在改变状态谓词。

例如“用银钥匙打开木箱”可能会检查：

玩家是否持有银钥匙。 目标是否是木箱。 木箱是否上锁。 银钥匙是否匹配木箱。 木箱是否已经打开。

然后更新：

boxLocked = false。 boxOpen = true。 hiddenLetterVisible = true。

这种谓词化模型让文本冒险具备可扩展性，而不是靠硬编码剧情分支。

六、核心范式三：错误反馈是玩法的一部分

在普通游戏中，错误操作往往只是无效。

但在文本冒险中，错误反馈非常重要。

如果玩家输入“砸开玻璃”，系统只回复“不能这样做”，体验会很差。更好的反馈是：

你敲了敲玻璃，声音很厚，似乎不是普通窗户。 你没有合适的工具。 你不想弄出太大声音。 玻璃已经有裂纹，也许某种更锋利的东西能派上用场。

错误反馈可以告诉玩家：

方向完全错误。 方向可能正确，但缺少工具。 目标存在隐藏状态。 需要更具体命令。 需要先观察其他线索。

因此 ResponseTemplate 不应只区分成功和失败，还应支持无效、条件不足、目标错误、工具错误、部分进展、重复尝试等反馈类型。

七、核心范式四：对象可操作性需要显式声明

文本冒险最怕“玩家想到合理操作，但系统不支持”。

如果房间描述里有一张桌子，玩家自然会尝试查看桌子、移动桌子、查看桌下、打开抽屉。如果系统只支持“查看房间”，玩家会感到世界是假的。

因此每个 WorldObject 应明确声明可操作性。

桌子可以查看、移动、检查下方。 抽屉可以打开、关闭、搜索。 书可以阅读、翻页、带走。 蜡烛可以点燃、吹灭、拿起。 NPC可以询问、给予物品、跟随、劝说。

对象不一定要支持所有合理动作，但不支持时需要合理反馈。

这套可操作性系统可以迁移到任何强调对象交互的游戏中。

八、事件与执行流程

一次典型命令执行流程如下。

玩家输入文本命令。

命令输入系统保存原始文本，并将其交给解析器。

解析器识别动词、目标对象、工具对象和修饰语，生成 CommandIntent。

解析器检查当前上下文是否存在歧义。如果有多个目标，系统请求澄清。

动作规则系统读取 CommandIntent、玩家状态、房间状态和目标对象状态。

若前置条件不满足，反馈系统生成解释性失败文本。

若条件满足，动作规则执行状态变化，更新 StatePredicate。

世界模型根据新状态刷新房间描述、可见对象、可达出口或NPC反应。

谜题系统检查是否推进了解谜节点。

记忆系统记录玩家已尝试的命令和已发现的信息。

反馈系统输出结果文本。

关键事件包括：

命令输入事件。 命令解析成功事件。 命令歧义事件。 动作前置检查失败事件。 动作执行事件。 状态谓词变化事件。 对象显现事件。 房间描述刷新事件。 谜题节点完成事件。 提示触发事件。

九、模块通信设计

建议采用“解析器—动作规则—世界状态—文本反馈”的管线。

输入系统不直接修改世界。

解析系统只负责理解玩家意图。

动作系统负责规则判断和状态更新。

世界模型维护对象、房间和谓词。

反馈系统根据动作结果生成文本。

谜题系统监听状态变化，而不是直接拦截命令。

UI系统展示文本、命令历史、背包和地图，不直接改变谜题进度。

这样可以避免命令解析、剧情脚本和世界状态混在一起，导致后续无法扩展命令、对象和谜题。

十、可扩展点

可以扩展为图形化冒险游戏的底层交互系统。玩家点击对象，本质上仍然生成 CommandIntent。

可以扩展为RPG对话外的环境交互，例如“调查、使用、组合、推动、阅读、偷听”。

可以扩展为AI NPC对话，让玩家输入自由文本，系统仍然将其归一到可执行意图。

可以扩展为解谜编辑器，设计师配置房间、对象、状态谓词和动作规则即可生成谜题。

可以扩展为多语言解析，支持中文、英文或关键词输入。

十一、失败隔离与调试设计

常见问题包括命令无法解析、对象别名缺失、玩家合理操作不被支持、谜题状态软锁、文本反馈误导、同一对象状态冲突。

调试工具应支持：

命令解析日志。 对象别名覆盖率。 当前房间可操作对象列表。 状态谓词查看器。 谜题依赖图。 玩家无效命令统计。 对象可达性检查。 软锁路径验证。

失败隔离上，主线谜题不应依赖唯一难猜命令。应提供多个动词别名、多个线索提示、重复观察反馈和替代路径。

十二、玩家体验目标

该类型最核心的体验不是：

我选择了正确选项。

而是：

我用自己的语言理解并操作了这个世界。

理想体验是：

读到房间描述。 注意到异常物件。 尝试不同命令。 从反馈中修正理解。 发现隐藏状态。 用合适对象和动作改变世界。 获得“这是我想到的解法”的满足感。

十三、可迁移设计思想

最值得迁移的是：

将玩家操作抽象为“意图”，再由世界对象和状态规则决定结果。

在Cocos或Unity框架中，这可以用于统一交互系统。按钮、点击、文本命令、AI行为都可以转化为 ActionIntent，再由规则系统处理。

在RPG中，可用于环境调查、物品组合、对话外行为。

在解谜游戏中，可用于对象状态机。

在沉浸式模拟中，可用于统一“使用、移动、破坏、组合、观察”的交互管线。

十四、完整冒险边界与设计支柱

完整产品应覆盖“观察描述—形成意图—输入命令—解析执行—世界变化—获得新线索—推进或改写目标”的循环。解析器只是入口，真正支撑游戏的是可持续探索的世界模型和因行动而变化的叙事。

核心支柱包括语言可预期、世界规则一致、失败有新信息、叙事允许回看。扩充同义词不能替代内容设计；新命令只有在多个对象和场景中形成稳定语义时，才值得进入核心动词集。

作品还需明确规模边界：房间数量、核心动词、可移动对象、角色日程和结局条件共同决定作者能否保证组合反馈，而不是只计算文本字数。

十五、回合、解析与世界状态

一次输入依次经过分词、指代消解、意图识别、前置条件检查、规则执行、时间推进和反馈生成。失败发生在哪一步必须可区分，例如“不理解动词”“对象不明确”“动作被世界规则阻止”不能都返回同一句无效提示。

世界状态至少记录地点、对象属性、容器关系、角色位置、知识状态和已发生事件。叙述只暴露玩家角色能够感知的信息，调试层则保留完整状态，避免作者为制造悬念破坏规则一致性。

回合推进要明确哪些命令消耗时间。查看背包、请求帮助与纠正歧义通常不应触发敌人行动，否则学习界面本身就成为惩罚。

十六、叙事进程与内容生产

长期进程可由目标、知识与世界改变共同推动。玩家获得一个答案，不只点亮任务节点，还可能解锁新称呼、新推断和对旧地点的重新解释。

内容单元可定义为“场景 + 可交互对象 + 动词规则 + 知识门槛 + 状态变化 + 反馈变体”。作者应优先编写规则可复用的对象类别，再为关键组合提供独特文本，避免组合数量随着内容线性失控。

叙事分支需区分局部状态差异和真正改变后续结构的分岔。没有后续影响的语气差异可以保留为表达，但不应伪装成路线选择。

十七、软锁恢复、提示与可访问性

系统应自动检测关键物品被永久丢弃、唯一角色不可达、目标前置条件被破坏等软锁。优先通过世界内补救、替代解法或局部回退恢复，而不是要求玩家重开整个故事。

提示分为复述当前目标、指出可调查范围、提醒相关动词和展示直接解法四级。玩家主动请求后逐级展开，且求助命令不推进危险时间。

输入历史、可点击名词、已知动词列表、字体与朗读选项属于可访问性基础。辅助输入不降低谜题本身的推理要求，只减少与解析器猜词搏斗的成本。

十八、作者工具、最小切片与验收标准

作者工具需要世界图、对象与容器检查器、规则优先级追踪、命令语料回放、不可达状态扫描和逐回合存档差异。测试语料应包含同义词、歧义指代、连续失败和撤销恢复。

最小切片包含五个相连场景、八个核心动词、一个会移动的角色、一个多解谜题和一次可恢复的错误操作。它必须形成从观察到推断再到世界改变的完整短篇，而非解析器演示。

验收时至少确认：常见意图有稳定表达；失败反馈指出下一步理解方向；世界状态不因描述变化而矛盾；谜题存在可验证解法；通关路径外的合理组合也获得恰当回应。
