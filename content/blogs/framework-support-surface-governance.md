# 支持面治理：代码总量为什么不等于产品能力

> 系列：大型 Unity 框架的治理复盘
>
> 日期：2026-08-01
>
> 状态：草稿
>
> 核心问题：一个框架拥有更多包、程序集和功能入口后，为什么仍不能据此宣称自己支持了更多产品能力，甚至可能变得更难维护和交付？

[系列目录](../blog.html)

开发一个大型框架时，很多进展都很容易被计数：

- 新增了多少个包；
- 增加了多少个程序集；
- 提供了多少种安装预设；
- 接入了多少个运行时后端；
- 出现了多少个示例、向导和编辑器面板；
- 支持了多少种配置组合。

这些数字增长时，仓库看起来会越来越完整。

目录更丰富，README 更长，安装器里的选项更多，架构图也覆盖了更多领域。维护者很容易得出一个直觉判断：

> 框架拥有的代码越多，能够对外提供的产品能力就越多。

但代码存在、功能可运行和产品承诺成立，是三件不同的事。

一个模块可以已经写完，却没有真实项目使用过；可以在本地示例中运行，却无法在干净项目中安装；可以在一个 Unity 版本下编译，却没有跨平台验证；也可以已经公开，却没有迁移策略、故障诊断或长期维护责任。

所以，评估大型框架时，真正需要统计的不只是代码里有什么，还要统计团队准备长期为什么负责。

## 先说结论：框架规模描述“拥有什么”，支持面描述“承诺什么”

**支持面（即“真正要负责的范围”）**：框架明确承诺可以被用户采用，并愿意持续维护其安装、使用、兼容、诊断、迁移和验证责任的能力集合。

支持面不是包目录的同义词。

一个功能进入支持面，通常意味着团队至少愿意回答：

- 用户从哪里开始接入；
- 默认需要安装哪些依赖；
- 支持哪些 Unity、平台和后端；
- 哪些用法属于正式合同；
- 失败时在哪里查看原因；
- 升级时如何迁移；
- 回归测试覆盖哪些关键路径；
- 出现问题后由哪个模块或维护者负责。

因此，一个仓库可以拥有一百多个包，但只正式支持其中很小的一组。

这不一定代表项目失败。

只要生命周期边界明确，它反而比“所有东西看起来都能用，但没有人知道哪些真的受支持”更加诚实。

## 代码仓库中至少存在三种不同的范围

评估框架能力时，需要先区分三个概念。

**实现面（即“仓库里已经有的东西”）**：已经存在源代码、配置、测试、文档或实验适配器的全部内容。

**消费面（即“别人实际拿来用的东西”）**：能够从公开入口安装、配置并在真实项目中组成有效闭包的能力。

**支持面（即“团队正式接住的东西”）**：团队愿意长期维护兼容性、验证矩阵、文档、迁移和故障责任的消费能力。

三者之间通常是逐层收缩的关系：

```mermaid
flowchart LR
    A["实现面<br/>代码、实验、原型、适配器"] --> B["消费面<br/>可安装、可配置、可运行"]
    B --> C["支持面<br/>有合同、有验证、有迁移责任"]
```

模块进入实现面，只需要代码存在。

模块进入消费面，需要真实入口和完整依赖闭包。

模块进入支持面，则需要长期责任。

把这三层混在一起，最常见的结果是：

- 实验代码被用户误认为稳定能力；
- 示例成功被误认为通用项目可以采用；
- 一次构建通过被误认为平台长期受支持；
- 模块数量被误认为产品成熟度；
- 维护者无法判断哪些破坏性修改真正需要迁移。

## 一组历史快照说明了什么

以下数字来自 2026 年 7 月 27 日至 7 月 30 日的仓库审计快照，不代表文章发布时的实时状态。

| 审计日期 | UPM 包 | 程序集 | Supported | Preview | Experimental | Evidence Backlog |
|---|---:|---:|---:|---:|---:|---:|
| 2026-07-27 | 140 | 750 | 4 | 101 | 23 | 39 |
| 2026-07-28 | 140 | 750 | 4 | 101 | 23 | 41 |
| 2026-07-29 | 140 | 750 | 4 | 101 | 23 | 44 |
| 2026-07-30 | 144 | 772 | 4 | 105 | 23 | 51 |

四天内，仓库增加了新的包、程序集和能力切片，但 Supported 包数量没有变化。

这组数据不应被简单解释为：

> 新增内容都没有价值。

更准确的解释是：

> 实现面继续扩大，但正式支持承诺没有同步扩大。

只要新增能力仍处于 Preview 或 Experimental，这种状态可以是合理的。

真正需要警惕的是，仓库的入口、文档和宣传是否仍然把这些不同生命周期的内容放在同一个平面上，让用户误以为它们拥有相同成熟度。

## 包数量是组织结构，不是产品能力数量

一个 UPM 包通常用于表达：

- 代码所有权；
- 依赖边界；
- 可选安装；
- 平台隔离；
- 生命周期差异；
- 第三方适配；
- 编辑器与运行时分离。

因此，拆包本身可以是正确的架构动作。

例如，一个原本同时承担以下职责的大包：

- 引擎无关的 Manifest 和 Resolver；
- Unity 路径及 Addressables；
- Lua、Wasm 或托管代码加载；
- HybridCLR 适配；
- 编辑器安装和诊断；

可以拆成职责更明确的 Core、Unity、Code 和 HybridCLR 层。

这可能降低最小消费项目的依赖闭包，也能避免没有使用 HybridCLR 的项目被迫安装对应适配器。

但拆包只有在以下条件成立时，才真正减少了支持负担：

1. 用户可以通过少数明确入口选择能力。
2. 默认安装不会重新把所有包聚合回来。
3. 包之间的可选关系可以被工具正确解析。
4. 文档能够说明每个包负责什么、不负责什么。
5. 测试围绕真实消费闭包，而不是逐包孤立运行。
6. 兼容聚合包只承担迁移，不继续发展第二套行为。

否则，拆包只是把一个复杂系统变成了更多名字。

代码所有权可能更清楚，但用户选择、验证矩阵和发布责任反而更复杂。

## 组合面为什么会比模块数增长得更快

**组合面（即“所有可能拼法”）**：包、Profile、平台、Unity 版本、后端和可选依赖之间能够形成的有效或无效组合。

假设一个框架拥有：

- 多个基础包；
- 多种安装 Profile；
- Mono 与 IL2CPP；
- Windows、macOS、Linux、Android 和 iOS；
- Addressables、脚本沙箱及可选后端；
- 若干 Unity 版本；
- 多组条件程序集和 Optional Bridge。

真正需要考虑的不是单独验证每一个模块，而是它们如何组合。

```text
模块
× Profile
× Unity 版本
× 目标平台
× Scripting Backend
× 可选依赖
× 项目配置
```

并不是所有组合都需要正式支持。

但如果项目没有明确裁剪，用户会自然假设公开入口之间可以自由组合。

这会导致一种典型错觉：

> 仓库只新增了四个包，所以维护成本只增加了四份。

实际增加的可能是：

- 新的安装闭包；
- 新的条件编译路径；
- 新的 Player 构建组合；
- 新的文档分支；
- 新的升级迁移路径；
- 新的故障归属争议；
- 新的“这个组合到底支不支持”的用户问题。

支持面治理的目标不是验证所有理论组合，而是明确宣布：

- 哪些组合是正式路线；
- 哪些只用于实验；
- 哪些明确不支持；
- 哪些需要消费项目自行负责。

## 生命周期不是标签，而是一份责任合同

Supported、Preview 和 Experimental 不应该只是清单中的颜色。

它们需要对应不同承诺。

| 生命周期 | 合理承诺 |
|---|---|
| Supported | 默认入口稳定；公共合同受控；有迁移策略；关键平台和闭包持续验证 |
| Preview | 允许真实项目试用；API 仍可调整；需要明确限制、风险和升级方式 |
| Experimental | 用于验证方向；默认不安装；可能缺少完整工具、平台和兼容保证 |
| DocsOnly | 设计和研究存在，但不暗示运行时实现已经成立 |
| Frozen | 保留兼容或历史读取能力，不继续扩展新行为 |

这里最重要的一条是：

> Preview 不是“质量比较差的 Supported”。

Preview 表示产品合同仍在形成。

它可以拥有大量测试，也可以解决真实问题，但维护者仍保留调整 API、闭包和实现方式的权利。

同样，Experimental 也不应因为示例运行成功，就自动出现在默认安装器的主入口中。

生命周期必须影响：

- 安装器中的可见性；
- README 中的推荐顺序；
- API 兼容政策；
- CI 覆盖范围；
- 发布清单；
- 用户遇到问题时的支持责任。

## 一个模块“能运行”还不等于“可消费”

**可消费能力（即“别人拿来就能用”）**：用户能够从明确入口完成安装、配置、首次运行、失败诊断和基本升级的完整能力。

可消费能力至少需要一条连续路径：

```mermaid
flowchart LR
    A["发现能力"] --> B["选择正式入口"]
    B --> C["解析依赖闭包"]
    C --> D["完成安装与配置"]
    D --> E["运行最小示例"]
    E --> F["在真实项目中接入"]
    F --> G["诊断失败"]
    G --> H["升级或卸载"]
```

如果链路在任何位置完全依赖维护者的隐性知识，用户实际得到的仍然只是源代码，而不是产品能力。

常见断点包括：

- README 只写了模块名称，没有接入顺序；
- 安装器能装包，但不知道项目还需要哪些业务绑定；
- Sample 使用了仓库内部路径；
- 示例依赖未登记的本地配置；
- Editor 中运行成功，Player 无法构建；
- 失败时只有空异常或没有诊断；
- 卸载后残留配置和程序集；
- 升级后旧存档或旧配置没有迁移路径。

因此，判断一个模块是否应该进入正式支持面时，不应只问：

> 代码写完了吗？

还要问：

> 一个不了解内部实现的项目成员，能否独立完成整个消费过程？

## 支持单位应当是用户路径，而不是源码目录

大型仓库容易围绕包和计划组织证据：

```text
包 A 测试
包 B 测试
包 C 测试
适配器 D 测试
工具 E 测试
```

但用户通常不会单独消费这些内部切片。

用户消费的是：

- 最小 Core 项目；
- Bootstrap Lite 项目；
- Data-only Mod；
- Unity Asset Mod；
- 带 Lua 或 Wasm 的脚本扩展；
- IL2CPP 下的 HybridCLR 热更项目；
- 带 UI、Save 和 Config 的完整 Runtime Starter。

因此，更合理的支持单位是**消费场景**。

例如：

| 消费场景 | 应覆盖的内容 |
|---|---|
| Core Only | 最小包闭包、初始化、Player 启动 |
| Bootstrap Lite | Bootstrap、Event、Pooling、生命周期和最小 Sample |
| Data-only Mod | Manifest、Resolver、配置、存档、更新与回滚 |
| Unity Asset Mod | Unity 路径、Addressables、场景和 Player |
| Managed Code Mod | 默认拒绝、信任策略、沙箱或 HybridCLR、重启边界 |

这样可以把几十个内部模块收敛为少数用户能够理解的产品路径。

包仍然负责代码组织，消费场景负责产品承诺。

## 兼容聚合包不是新的正式产品

框架拆包后，通常需要保留旧入口。

一个兼容聚合包可以：

- 继续接受旧 manifest；
- 安装新的职责包；
- 保留旧程序集身份；
- 给旧项目提供迁移窗口。

但它不应该继续：

- 增加独立运行时行为；
- 形成第二套更新引擎；
- 拥有与新包不同的故障语义；
- 被新项目文档继续推荐；
- 永久承担全部新能力的聚合入口。

**兼容面（即“旧项目缓冲区”）**：为了让既有用户逐步迁移而暂时保留的入口、类型和行为集合。

旧项目缓冲区的目标是缩短，而不是增长。

它需要明确：

- 新项目应该使用什么；
- 旧入口何时停止增加功能；
- 哪些行为只是适配；
- 迁移需要哪些步骤；
- 何时允许发生 Preview breaking change。

如果兼容入口继续获得新能力，它最终会重新变成拆包前的大包。

## 支持面扩大需要消耗维护预算

**维护容量（即“团队照料得过来的规模”）**：团队能够持续验证、解释、修复、迁移和发布的产品范围。

支持一个能力的成本不仅发生在首次开发时。

后续还会持续产生：

- Unity 版本适配；
- 平台 API 变化；
- 第三方依赖升级；
- 安装器和 Sample 维护；
- 文档更新；
- API 兼容评估；
- 用户问题诊断；
- CI 时间和 Runner 资源；
- 存档及配置迁移；
- 安全修复；
- 发布说明。

因此，支持面扩大应该是一项显式决策：

```text
新增用户价值
> 新增长期维护成本
+ 新增验证成本
+ 新增迁移成本
+ 新增故障责任
```

如果团队只计算功能开发收益，却不计算长期照料成本，框架会逐渐进入一种状态：

- 每个模块看起来都接近完成；
- 没有任何模块真正达到稳定；
- 新功能不断进入 Preview；
- Evidence Backlog 持续增长；
- 文档和状态开始落后；
- 维护者不敢删除旧入口；
- 用户无法判断推荐路径。

这不是单纯的技术债。

它是支持承诺超过维护容量之后形成的产品债。

## 如何缩小支持面，而不必删除已有代码

支持面治理不等于大量删代码。

很多时候，可以通过重新组织承诺降低维护负担。

### 1. 建立少量正式 Profile

不要让用户从一百多个包中自行猜测组合。

提供少量经过验证的正式闭包，例如：

- Core Only；
- Bootstrap Lite；
- Data Mod；
- Unity Asset Mod。

Profile 之外的组合可以存在，但不自动获得相同支持等级。

### 2. 让实验后端默认关闭

第三方运行时、脚本语言、平台 Adapter 和特殊构建链应显式选择。

“代码已经存在”不代表默认项目需要承担它们的依赖和风险。

### 3. 使用 Optional Bridge 降低默认闭包

如果 Config、Save、Addressables 或某个后端不是所有用户都需要，应优先通过条件程序集或可选 Bridge 接入，而不是让最小 Core 强制依赖全部能力。

### 4. 为每项能力指定唯一 Owner

安装器、运行时、Sample 和文档可以协作，但不能各自实现一套相似规则。

同一事实只应有一个直接 Owner，其他入口通过查询或适配复用。

### 5. 将兼容入口设为只减不增

兼容包允许修复迁移问题，但不再成为新能力入口。

### 6. 分离“存在”和“推荐”

Catalog 可以完整列出仓库能力。

README、安装器默认页和 Quickstart 只展示当前推荐路径。

### 7. 用真实消费链决定验证范围

测试应优先保护用户实际采用的 Profile 和 Sample，而不是平均对待每个源码目录。

## 几种常见误判

### 误判一：包越多，框架越通用

包越多可能表示边界更清晰，也可能只是职责被过度切碎。

是否通用，需要看用户能否用少量稳定入口完成真实项目。

### 误判二：模块处于仓库中，就属于产品能力

研究代码、适配原型和 Experimental 后端都可以存在，但不应自动进入产品承诺。

### 误判三：Sample 能运行，就代表能力可支持

Sample 可能依赖固定版本、内部配置和维护者知识。

正式支持还需要干净安装、Player 构建、诊断和迁移路径。

### 误判四：拆包一定降低复杂度

拆包降低了源码耦合，不一定降低用户选择、测试组合和发布责任。

### 误判五：所有 Preview 都应该尽快升为 Supported

有些 Preview 用于长期试验或特定项目，不一定值得承担稳定合同。

### 误判六：支持更多平台只需要多跑几次构建

平台支持还涉及输入、文件系统、线程、AOT、原生依赖、生命周期、发布流程和持续回归。

## 我的支持面检查清单

在把一个能力提升为正式支持之前，我会检查：

1. 它解决的是明确用户问题，还是只补充了架构完整性？
2. 用户是否拥有唯一且清楚的推荐入口？
3. 默认依赖闭包是否与能力价值匹配？
4. 是否存在真实消费项目或 Fixture？
5. Editor、Player 和目标平台边界是否明确？
6. 生命周期状态是否影响安装器和文档可见性？
7. 公共 API 是否具备兼容和迁移政策？
8. 失败时是否能输出结构化诊断？
9. 卸载、取消和升级是否有明确语义？
10. 是否与另一个包重复拥有同一行为？
11. 兼容聚合包是否只承担迁移？
12. 该能力应由哪个 Profile 或用户路径负责验证？
13. 团队是否拥有持续运行这些验证的资源？
14. 新增支持承诺后，需要维护多少平台和组合？
15. 文档是否明确说明哪些情况不受支持？
16. 维护者是否愿意在未来版本继续为它处理问题？
17. 如果暂不提升为 Supported，用户是否仍能安全试用？
18. 如果停止维护，是否存在清晰的降级和退出路径？

只要其中多项没有答案，这项能力就更适合继续保留在 Preview 或 Experimental，而不是通过修改标签获得虚假的成熟度。

框架的产品价值，不在于仓库能够容纳多少代码。

它取决于维护者能否把复杂的内部系统压缩为少数清楚、可信并能够长期负责的用户路径。

真正成熟的框架不需要承诺所有东西。

它需要准确地知道：

> 哪些能力已经存在，哪些能力别人能够采用，以及哪些能力团队准备长期接住。
