# IrisSakura 四项目品牌体系：一体化设计与过渡方案

> 版本：v1.0 设计提案  
> 日期：2026-09-10  
> 适用项目：Iris Engineering、SakuraGameFramework、Myosotis、Violet Shelf，以及 IrisSakura 个人站。  
> 本轮状态：命名方向已由用户确认；本文给出定位、视觉、文案、站点和过渡的完整推荐方案。视觉稿、代码修改、构建、提交与发布尚未执行。  
> 阅读方式：本文独立成立，不要求拼接前稿。后续新决策应回写本文或其被正式指定的源版本，不另建一组互相冲突的补充方案。

## 0. 决策摘要与适用边界

采用“创作者总品牌背书、四个项目各自独立”的结构，而不是继续要求所有项目归入 Iris 或 Sakura 两大家族。

| 品牌层级 | 名称 | 面向使用者的职责描述 | 本轮处理 |
|---|---|---|---|
| 创作者总品牌 | IrisSakura | 研发、研究与创作的共同署名 | 保持名称与既有识别，不重做总标志 |
| 工程项目 | Iris Engineering | 工程组织与受控交付 | 保留定位主体、名称、既有标志与主色 |
| 游戏框架 | SakuraGameFramework | 可复用的游戏开发能力 | 保留锁定名；Sakura Framework 继续作为既有展示名称 |
| 知识项目 | Myosotis | 研究、设计与创作资料库 | 建立独立项目品牌；本版使用单名，不把 Library 等后缀视为已批准名称 |
| 桌面工具 | Violet Shelf | 本地开发与创作工具台 | 由 Iris Shelf 过渡；保留 Shelf 后缀和已有产品能力 |

**核心主张：四个项目拥有各自的身份，可以互相协作，但不必互相依赖。**

品牌确认并不自动批准新功能、公开私有资料、迁移技术身份、改名仓库、重建部署、执行 Electron 迁移或发布新版本。本文中的实施章节用于界定将来的工作范围，不构成远端写入或部署授权。

### 0.1 已确认与本版设计建议

已确认的是总品牌 IrisSakura，Iris Engineering 与 SakuraGameFramework 保持不变，文档库使用 Myosotis，桌面产品使用 Violet Shelf。

本版设计建议包括：Myosotis 以单名加职责副标题对外呈现；两套新视觉采用的花形、配色和口号；网站导航与页面组织；先更新品牌呈现、暂不改技术身份的过渡方式。这些建议已经在本文收敛为一套完整方案，不再把命名选择题交回用户。

### 0.2 本轮明确不做

不新增 Flora、Garden 等更上层平台品牌；不把每个模块分配一朵花；不重做 Iris/Sakura 已确立的视觉；不把 Myosotis 建成新笔记软件；不因改名创建统一数据库、对象注册服务或跨仓 SDK；不重命名 Iris Core、既有游戏和独立 CLI；不把品牌工作扩成全部基础设施补完工程。

## 1. 真实基线与这次调整解决的问题

### 1.1 已核对的现有事实

个人站现有 `config/brand.json` 仍以 Iris、Sakura 和 Journal 组织能力品牌；Journal 的展示名为 IrisSakura Journal。旧品牌规范将 Sakura Design Journal 标为过时公开名称，但允许 `sakura-design-journal` 等内部身份继续保留。[R1][R2]

文档库 HOME 已经以知识工作台为入口，连接源码研究、设计、审计、博客和个人规划。它不再只是某个框架的使用文档。[R4]

Shelf 的桌面说明已经包含卡牌编辑、素材关联、配表关系、数值实验、动效预览和本地化检查。它与 Iris Engineering 是可选互操作，而不是必须一起运行的同一产品。[R5]

Shelf 源仓还管理独立 CLI，根 README 明确说明仓库只是源码管理便利，不代表共享运行时；Personal Tool Garden 是内部孵化与维护制度，不是替代产品品牌。[R6]

桌面配置仍为 `productName: Iris Shelf`、窗口标题 `Iris Shelf`、应用标识 `com.irissakura.shelf`。本版以这些已读配置作为过渡起点，不凭产品新名称推导新标识。[R7]

现有 Iris 主色已经是蓝紫色 `#4C3DF5`，Sakura 主色为 `#DB4F8A`。所以“让 Violet 使用紫色”本身不足以完成辨识；必须同时区分色相倾向、花形、布局与界面节奏。[R3]

### 1.2 需要解决的品牌问题

旧结构容易让文档库看起来是框架资料室，让 Shelf 看起来是工程控制面的附属界面。新结构要承认它们已经具备独立使用目的，同时保留同一创作者的连续性。

新的品牌叙述也不应再把所有活动压成“研究 → 工程 → 框架 → 游戏”的必经流水线。研究可以独立成立，工具可以服务框架之外的创作，游戏也可以只采用其中一部分能力。

### 1.3 方案比较与最终选择

| 结构选择 | 优点 | 主要问题 | 裁决 |
|---|---|---|---|
| 保持 Iris/Sakura 两大类，新增名称仍作为下属 | 改动少 | 没有解决独立项目身份问题 | 不采用 |
| 四个完全独立、互不呈现关联的品牌 | 个性空间最大 | 削弱 IrisSakura 的共同积累，维护四套体系成本较高 | 不采用 |
| IrisSakura 背书的四个独立项目 | 保留共同身份，同时解释各自用途 | 需要清晰的命名、视觉与展示规则 | 采用 |

## 2. 品牌架构与关系

### 2.1 总品牌与项目品牌

IrisSakura 回答“谁在创造和维护这些东西”；项目名称回答“这是什么、解决什么问题”。

IrisSakura 名字中的 Iris/Sakura 不再是一份限制项目数量的分类表。增加 Myosotis 和 Violet，并不要求把创作者名称改成四种花的拼接。

四个项目在品牌总览中同级。同级不是承诺功能一样成熟、代码体量一样大、投入一样多，也不是要求四个项目都变成应用程序。

### 2.2 联合标识与成果

`IRIS × SAKURA` 继续用于 Iris Engineering 与 SakuraGameFramework 的直接协作，不再作为所有项目共同出现时的唯一总标题。[R2]

四项目总览使用 IrisSakura 加四个独立项目标识，不制造 `IRIS × SAKURA × MYOSOTIS × VIOLET` 这种过长的常规字标。既有 IrisSakura 总标志继续代表创作者身份，不要求把四朵花挤进一个新图标。

游戏保持自己的作品名；Consumer Lab 仍是采用和验证层，不升级为第五朵花。已有 Iris Core 等范围明确的项目名称，不因这次品牌调整被自动重新分配。

### 2.3 署名规则

单项目页面以项目名为第一层、职责说明为第二层、`by IrisSakura` 为第三层。总品牌署名建议为项目标题视觉字号的约三分之一，不与产品名争夺第一视线。

总览页面使用四张同一层级的项目卡。单项目页面不要求持续展示其他三个项目，只在“相关项目”或页脚提供明确链接。

## 3. 正式名称、简称与后缀

| 对象 | 正式使用 | 允许的语境内简称 | 不应混淆的对象 |
|---|---|---|---|
| 创作者 | IrisSakura | 无新增简称要求 | 不是必须安装的宿主平台 |
| 工程项目 | Iris Engineering | 工程上下文中的 Iris | 不等于所有工程相关工具的强制前缀 |
| 游戏框架 | SakuraGameFramework；既有展示名 Sakura Framework | 框架上下文中的 Sakura | 不等于任何使用框架的游戏名 |
| 知识项目 | Myosotis | 保持完整拼写 | Journal、Archive、Library 不自动成为第二个同级品牌 |
| 桌面产品 | Violet Shelf | 已明确产品上下文中的 Shelf 或 Violet | 不等于整个源码仓中的全部 CLI |

框架 README 明确区分锁定名 SakuraGameFramework 与面向安装、文档和运行时消费的 Sakura Framework；本轮延续，不另外发起一次框架命名统一工程。[R11]

### 3.1 Myosotis 后缀处理

本版页面标题和 README H1 使用 **Myosotis**，副标题使用“研究、设计与创作资料库”。英文描述使用 `Research, Design & Creative Knowledge`，这是职责说明，不是新产品名。

Library 可以描述资料库的性质；Journal 可以描述公开文章与持续研究栏目；Archive 可以描述历史材料区域。三者均不与 Myosotis 竞争项目身份。

### 3.2 大小写与检索

正文使用 Iris Engineering、SakuraGameFramework、Myosotis、Violet Shelf。全大写只用于装饰性字标，不替代代码标识，不在正文中随机混用。

新的公开标题、页面描述和搜索元数据尽量使用完整项目名与 IrisSakura 署名，避免仅以 Violet 这种单词承担全部可检索性。本文没有完成商标、域名、应用商店或包名可用性审查，也不宣称这些名称独占。

## 4. 四个品牌的定位

### 4.1 Iris Engineering：让工程推进有据可依

主要对象是项目负责人、开发者以及参与工程执行的 Agent。它组织项目事实、任务上下文、授权、运行结果与交付证据，使工作能够被接续和追溯。

保留既有口号 **Engineer · Manage · Deliver.** 当前 README 的职责边界是可选、引擎无关的工程事实与受控交付系统，不接管游戏 Runtime、工具宿主或模型能力。[R10]

品牌气质是清晰、有序、可靠，而不是“处处设卡”。页面应先展示它怎样减少工程混乱，再说明执行与证据边界；不要以密集门禁术语作为第一层营销表达。

### 4.2 SakuraGameFramework：让游戏能力可以组合与生长

主要对象是游戏开发者与消费项目。它提供可组合的运行时服务、玩法能力和适配边界，而不是预先规定每款游戏应该长成什么样。

保留既有口号 **Frame · Power · Extend.** 对外持续区分引擎无关目标与当前平台支持事实，不把 Godot 局部适配宣传成完整双引擎等价。[R11]

品牌气质是可组合、可扩展、具有生长感。保持既有图形和色彩资产，只在总览关系及相关项目说明处更新。

### 4.3 Myosotis：让积累留得住，也用得上

主要对象首先是创作者本人，其次是访问已授权公开材料的读者。它长期保存研究、设计与创作资料，并通过主题、来源和联系帮助材料再次参与思考。

推荐中文主张：**让积累留得住，也用得上。**

推荐英文主张：**Keep · Connect · Rediscover.**

Myosotis 不把所有内容都变成生产资料。一次观察、一段原创文字、一份尚未成熟的设计，即使暂时没有应用目标，也可以有保留价值。

品牌定位允许未来容纳文学与创作材料，但本轮不宣称这些领域已经具备专用编辑器、自动身份关联或完整备份功能。现有内容与未来承载方向必须分开说明。

### 4.4 Violet Shelf：常用工具，就在手边

主要对象是开发者与创作者本人。它把常用工具、项目入口和局部实验放在清晰的本地使用界面中，支持从输入材料到观察结果的具体操作。

推荐中文主张：**常用工具，就在手边。**

推荐英文主张：**Tools within reach.**

Violet Shelf 不被定位为“所有事情的控制中心”，也不只是文件收藏架。它提供独立工具与共享使用入口，但不自动接管代码仓库、任务授权、全部源素材或外部项目的数据。

原有 `Enter your workspace.` 可以保留为产品引导语，不再承担完整品牌定位。新的正式介绍不以“the companion to Iris Engineering”为第一句话；可选互操作放在后面的关联说明。

## 5. 协作边界：共用关系，不混淆所有权

| 问题 | 主要责任位置 | 其他项目如何参与 |
|---|---|---|
| 某份研究或原创文字的来源、论述和修订 | 该内容的原始所有者；在 Myosotis 中维护的内容由 Myosotis 承载 | 其他工具引用，不默默复制出第二份权威正文 |
| 卡牌编辑文档、素材采用关系、数值实验 | 产生该对象的具体工具或项目 | 可关联知识来源，不因品牌统一改变存储所有权 |
| 模块安装、代次、任务和历史重算 | Violet Shelf 的既有 Workbench 运行基础 | 不由 Myosotis 或 Engineering 重建同一状态机 |
| 工程任务、授权与交付证据 | Iris Engineering | Shelf 可展示；Myosotis 可保存研究，不授予执行权限 |
| 运行时能力与引擎适配 | SakuraGameFramework | 工具可以产生输入；Framework 不承载全部创作源文件 |
| 公开内容与网站出版 | 来源的公开许可加站点发布边界 | 更换品牌名不扩大原有公开范围 |

一个可能的未来协作场景是：Myosotis 保存原创文字；Violet Shelf 中的卡牌文档引用该文字来源，并组合素材；游戏项目消费导出结果；Iris Engineering 在需要时记录任务与交付。**这只是边界示例，不是声称今天已经存在全链路自动集成，也不要求每次创作都经过四个项目。**

已有稳定 ID、来源版本、模块代次与文档引用应继续保留。为了品牌一致性新建“全局花卉对象平台”不在本轮范围。

## 6. 共同视觉系统

### 6.1 统一什么，区分什么

共同部分包括字体使用规则、基础间距、清晰的文本层级、图标绘制精度、无障碍要求与 IrisSakura 署名方式。差异来自各自的轮廓、强调色、图案、信息组织和动效节奏。

| 品牌 | 主导形态 | 界面组织 | 视觉动词 | 不采用的捷径 |
|---|---|---|---|---|
| Iris | 沿用既有工程标识；直线、轨道、节点 | 清晰分区与状态关联 | 对齐、推进 | 以“复杂”表示专业 |
| Sakura | 沿用既有框架标识；分枝、层次、组合 | 能力分组与依赖关系 | 组合、展开 | 将花瓣铺满工作界面 |
| Myosotis | 圆润五瓣、中心留白、索引标记 | 阅读、主题、来源与关联 | 留存、连接、重访 | 巨大默认知识图谱或陈旧档案室视觉 |
| Violet | 上轻下稳的堇花轮廓、短水平基线 | 工具集合与专注工作区 | 取用、操作、归位 | Iris 图标换紫色，或另做通用仪表盘 |

花的象征意义由项目实践逐渐建立。本文中的“记忆”“日常工具”等是品牌叙事，不宣称为普遍、唯一或经过科学验证的花语。

### 6.2 字体与排版

优先复用各仓已经安装或打包的字体，不增加跨网络字体依赖。产品 UI 使用原有无衬线家族与平台中文回退，代码保持等宽字体。Myosotis 的长文主题可以使用既有阅读字体，但不要求为了“文学感”全站更换衬线字体。

新字标与 Iris/Sakura 现有字标使用同一家族或经过明确协调的字形。Myosotis 名称较长，应优先给足宽度，不以极窄字距强行塞入短标题容器。

设计目标：网页正文 16–18 CSS px，长文行高约 1.7–1.85；桌面主要操作文字以 14–16 CSS px 为起点。数字是本版设计起点，不是对现有界面的审计结论。

### 6.3 图标与插画分层

产品标志、功能图标和人物插画分别处理。功能图标保持语义明确，不把保存、删除、导出等按钮全部替换成花。

Iris/Sakura 既有人形设定可以继续作为品牌文化资产。Myosotis/Violet 可在未来扩展人物设计，但本轮不把新增两名角色、立绘或故事设定设为落地前提。人物插画不替代 Dock 图标、页面标题和工具操作区。

## 7. Myosotis 视觉设计

### 7.1 造型母题

采用勿忘草的圆润五瓣与清晰花心作为母题。RHS 对 Myosotis sylvatica 的描述包含蓝色五裂花及白色或黄色花心；本版从中提取轮廓，不追求植物插画的写实细节。[E1]

主标志建议为五个短圆瓣围绕一个明确的中心负形，整体近圆，但保留瓣间凹口。大尺寸扩展图形可以加入一段不闭合的索引圆弧或关联路径；不要将书本、放大镜、节点、花和字母 M 全部塞进一个小标志。

**识别重点：中心与重访。**花心可以被解释为被保存的内容，外部关系可以继续扩展。这个解释属于设计主张，不是图标使用者必须理解的谜题。

### 7.2 与 Sakura 的区别

两者都可能使用五瓣轮廓，因此不能只靠蓝粉差异。Myosotis 要更紧凑、圆润，中心更明确；与 Sakura 的辨识以实际现有资产并排核对为准，不擅自修改 Sakura 去配合新标志。

若单色小尺寸仍接近，应调整 Myosotis 的瓣形比例、中心负形与整体密度，而不是给旧品牌重新造型。

### 7.3 色彩与阅读氛围

以低饱和湖蓝、浅纸色和少量花心金色为主。它不采用与 Iris 相同的高饱和电蓝渐变，也不把知识资料包装成每页都需要“星空、网络和数据流”的技术产品。

金色只作为花心与少量装饰，不作为正文、链接或状态指示。文章正文继续由中性色主导，主题色用于标题点缀、当前主题、链接和来源标记。

### 7.4 主要应用

项目封面用 Myosotis 字标、职责副标题与一段短介绍。资料目录优先提供主题、文档标题、摘要、来源类型和更新信息；图谱只在具体关系确有帮助时出现。

公开页面按真实内容组织研究笔记、设计分析和公开综述。没有实际内容的“诗词馆”“角色百科”等栏目不为了品牌完整而提前开放。

动效以 140–200 ms 的轻微淡入或定位反馈为建议上限；阅读时不持续漂浮花瓣。支持 reduced motion，并不把动画作为理解关系的唯一方式。

## 8. Violet Shelf 视觉设计

### 8.1 造型母题

本版选择 Viola 类堇花作为主要造型参考，具体可参考 sweet violet；这是本轮视觉方向，不是用户此前已指定的植物物种。RHS 将 Viola odorata 记为 sweet violet，并描述其紫色或白色花及心形叶片。[E2]

主标志采用左右近似对称、上下不等重的花形。下部花瓣稍宽，给出稳定承托感；大尺寸可以加入一条很短的水平基线暗示 Shelf。小尺寸移除基线，仅保留花形和必要负形。

不要把 Violet 简化成与 Myosotis 相同的五瓣圆花。Violet 的识别依赖上下方向与承托形态，Myosotis 的识别依赖近圆结构和中心。

### 8.2 与 Iris 的区别

Iris 保留既有蓝紫主色和工程图形；Violet 使用偏梅紫、偏暖的紫色以及更柔和的中性底色。几何从工程轨道转为工具面板和水平工作台关系。

即便移除颜色，Violet 也应该能从 Iris 旁边被辨认出来。颜色不作为唯一身份，也不将“紫色”占为一个品牌独享的禁区。

### 8.3 工具入口与工作区

顶栏保留 Violet Shelf 识别；工具内部以工具名称和当前文档为主。进入 Card Studio 后，画布不能因为主品牌是 Violet 就给所有卡图套紫色；进入数值工具后，图表仍按系列、比较和状态表达，不强制单一品牌色。

工具库可以按已有用途分组，但不因改品牌重排所有操作。当前任务区建议采用：稳定导航、清晰工具标题、主要编辑面、结果或检查区。是否已有侧栏、分栏或面板应以产品当前交互为基线，不进行无关重写。

当前版本的 local-first、本地保存与可选互操作边界要在介绍中清晰，但不能把“本地”外推为零风险、自动备份或任意第三方代码沙箱。[R5]

### 8.4 文案与微交互

空状态应直接说明可执行动作，例如“选择一个工具开始”“导入卡牌文档”“选择素材目录”。避免大段世界观、拟人角色对话或需要用户学习的新花卉术语。

操作反馈建议 100–160 ms，强调状态变化而非展示动画。保持现有快捷键、焦点、选区、草稿和异步编辑归属；品牌迁移不得把真实交互回归当成装饰性变化。

### 9.2 本轮完成的色对计算

按 WCAG 的 sRGB 相对亮度方法计算，结果取两位小数。这里只证明下列不透明色对的数学对比度，不证明整个页面达到 WCAG。[E3]

改变 `.app` 或 DMG 的展示文件名可能涉及构建脚本、快捷入口和两份应用并存。后续实施应提供清晰的替换说明，不自动卸载旧包，不允许为了演示而同时启动两个共享同一数据位置的版本。

### 13.3 与 Electron 迁移的关系

品牌调整与桌面技术栈迁移是两项独立工作。若实施时 Tauri 仍为正式基线，按本文已读配置处理；若 Electron 迁移已经独立获得授权并成为新基线，则将品牌文案和视觉应用于该基线，但不得借此放松其数据兼容方案。

本轮不提高最低 macOS 版本，不更换运行时，不修改模块执行沙箱，不把 Windows 支持混入改名任务，也不为了“名称干净”更改已有模块格式。

### 13.4 模块与不可变材料

当前 `.wmod` 若已经以固定版本和摘要被安装、存档或重放，不直接修改包内显示名后仍沿用旧版本/旧身份。可在宿主展示层增加品牌说明；确需改包时按既有版本流程产生新材料，历史版本保持可读。

相同原则适用于内容目录、公开导出和审计记录：新内容使用新品牌，旧内容保留当时名称，来源映射在外层表达。

### 13.5 公开边界

现有文档库仅将被明确许可的文章全文导出，设计和审计等材料有不同公开边界。[R9] 新增 Myosotis 页面不授予更多内容公开权限，不把作者的文学收藏、媒体或私人短文自动加入网站。

如果产品截图需要用于 Violet 宣传，应使用明确选择的演示数据或已授权素材，不公开私人路径、未公开作品和凭据。

## 15. 实施与集中验收

### 15.1 一个版本目标，内部按职责施工

本轮完整交付目标为：**四项目品牌关系清楚、Myosotis/Violet 有独立识别、当前公开呈现一致、既有用户数据和引用不受损。**

内部可以由视觉、文档、网站、桌面不同职责分工，但不能把每个文件、每个 token 或每个文本替换变成一次人工批准和全量测试。

在设计与范围确认后连续完成可用版本，再集中验收。中途仅对已经观察到的失败、会明显扩大返工的关键假设或不可回退外部副作用做最小检查。保持用户既定的设计先行、连续实施、完整功能闭环后集中验收节奏。

### 15.2 推荐施工顺序

**第一段：品牌资产与身份清单。**核对当前源基线和不改动身份，完成两个新标志的矢量母版、字标、色板与并排视觉定稿。这是一次完整视觉产物，不要求每次画线后等待审批。

**第二段：并行完成各表面。**Myosotis 更新入口和说明；Violet 更新应用与产品文案；网站更新品牌登记、页面和生成物；Iris/Sakura 只更新关系引用。各仓保留各自所有权，避免跨任务覆盖。

**第三段：集中验收并记录限制。**对每个受影响产品执行一次覆盖对应真实路径的验收；发现问题后修复并复查受影响闭环，复用未变化范围的有效证据，不反复运行全部历史套件。

**第四段：独立决定交付与发布。**本地验收完成不等于已提交、推送、签名、公证或公开上线。远端操作只在另外明确授权的源仓和流水线范围内执行。

## 16. 风险、完成标准与后续维护

### 16.1 主要风险

| 风险 | 收敛策略 |
|---|---|
| Iris 与 Violet 都是紫系 | 保留 Iris 冷蓝紫；Violet 偏梅紫；以轮廓和布局共同区分 |
| Myosotis 与 Sakura 都有五瓣意象 | 新标志强调紧凑圆瓣和中心；与旧标并排调整，不重做 Sakura |
| 改名被误做成数据迁移 | 预先列出稳定身份；实际读写路径参与集中验收 |
| 各处名字短期不同步 | 一次更新当前入口和生成源；保留明确旧名映射，不重写历史 |
| 品牌范围变大被当成功能已完成 | 每个介绍分开写用途、已有能力和未来方向 |
| 两个新品牌带来更多维护负担 | 复用现有 token、生成器和资产管理，不新建公共平台 |
| 网站公开了更多私有资料 | 公开许可和导出边界不变；只更新名字与呈现 |
| 源仓和镜像身份混淆 | 明确 canonical 写入位置；GitHub 只读，既有同步另行授权 |

### 16.2 本版完成标准

当两个新品牌有可维护的正式视觉资产，当前文案与网站呈现一致，Violet 的旧数据与旧模块继续可用，Myosotis 的来源和公开边界保持，且 Iris/Sakura 既有身份未被破坏时，这一轮品牌化即可认为完成。

不需要等到四个项目功能一样多、全部工具达到长期可信、游戏正式发行、Windows 与 Godot 全覆盖，才允许结束本轮品牌工作。

### 16.3 后续维护原则

每个项目主要使用自己的品牌；跨项目文章仍由 IrisSakura 署名。新增工具默认用功能名，只有真正独立、长期存在且有清晰边界的项目，才讨论独立花卉品牌。

新的文案使用新名称，历史记录保留当时名称；维护一个明确别名关系即可。品牌方案的修改基于新的定位问题或使用问题，不因为工具数量增长而定期重命名。

**最终设计原则：IrisSakura 代表共同创作者，Iris、Sakura、Myosotis、Violet 分别形成清晰身份；它们之间靠真实协作建立关系，而不是靠强制依赖、统一数据库或越来越多的品牌层级维持一致。**
